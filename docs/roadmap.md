# Roadmap

Eight milestones. Each one is a state of the system, not a sprint. Milestones 1
and 2 are the current focus.

Status markers:

- `[x]` done and verified
- `[~]` partly done — there is code, but it is not finished or not proven
- `[ ]` not started

## 1. Skeleton

The repository, the services and a development environment that starts with one
command.

- [x] uv workspace: `apps/api`, `apps/orchestrator`, `apps/cli`, `apps/web`,
      `packages/shared`, `packages/workspaces`, `packages/api-client`
- [x] FastAPI control plane with `/api/v1` and an unversioned `/health`
- [x] React + TypeScript + Vite dashboard shell
- [x] PostgreSQL in `docker-compose.yml`, SQLite as the dev default
- [x] Makefile targets: `install`, `api`, `orchestrator`, `cli`, `workspaces`,
      `web`, `test`, `lint`, `fmt`
- [x] CI: ruff, pytest, web typecheck and build
- [ ] Database migrations (Alembic). Tables are created at startup today.

## 2. Kubernetes

A project becomes an isolated namespace with a PVC and a pod, with a lifecycle
the control plane drives.

- [x] Namespace naming from the configured prefix plus the project slug
      (`af-demo`)
- [x] PVC mounted at `/workspace`
- [x] Pod with code-server and the OpenHands Agent Server, and the isolation
      guarantees (no host mount, capability drop, non-root)
- [x] Service, and a NetworkPolicy derived from the agent's policy
- [x] The `WorkspaceProvider` contract with Kubernetes, Podman and Local
      implementations and a registry
- [x] Provider capability reporting (`GET /api/v1/providers`)
- [x] Workspace lifecycle from the API: idempotent provision and destroy, both
      accepted (`202`) and reconciled by the orchestrator
- [x] Secrets resolved and injected at workspace creation
- [x] Service account and cluster role for the orchestrator in the Helm chart
- [ ] A first successful provision against a real cluster
- [ ] The Podman provider exercised in CI (the binary is not present in the
      development environment)

## 3. OpenHands

The execution layer. The Agent Server runs in the workspace pod and agents
actually do work.

- [x] The Agent Server container is part of the workspace pod spec
- [ ] A client that matches the real Agent Server API (`openhands.py` targets an
      assumed shape today)
- [ ] Agent creation and task execution end to end
- [ ] Event streaming from the Agent Server into the event catalog
- [ ] Permission requests generated by the agent, not just recorded by a client
- [ ] Fix the agent manager's use of four event types that are not in the catalog

## 4. Development UI

The dashboard becomes usable for daily work.

- [x] Project list and project view shell
- [x] code-server embedded in an iframe
- [x] Agent panel, task panel and diff panel
- [x] A typed TypeScript API client (`packages/api-client`)
- [~] Event-stream hook (`useEventStream`) — written, but the dashboard's `/api`
      base path does not match the `/api/v1` prefix
- [ ] Point the dashboard (or the API client) at `/api/v1` and verify against a
      running control plane
- [ ] Files browser
- [ ] Terminal (WebSocket to the workspace)
- [ ] Permission and clarification dialogs a human answers in place

## 5. Multi-agent

Many agents per project, each on its own branch.

- [~] The agent model carries `branch` and a permission policy, and the git
      manager can create and commit to a branch
- [ ] Multiple concurrent agents per project
- [ ] Concurrent worktrees or workspaces so agents do not collide in one
      `/workspace`
- [ ] Branch-per-agent merge flow with conflict reporting
- [ ] Fleet-wide agent status and supervision

## 6. API

The API is the product surface. Most of this milestone has landed ahead of the
milestones it depends on.

- [x] Versioned REST API under `/api/v1`
- [x] WebSocket event streams with backfill (`project` and `agent` topics)
- [x] API keys: hashed, scoped, project-pinnable, revocable
- [x] Semantic actions: review / test / deploy
- [x] Webhook subscriptions with HMAC signing, retries and an SSRF guard
- [x] Event catalog discovery
- [x] Permissions: read the effective policy and answer a request
- [x] Secrets by reference: register, list, delete; resolution respects scope
- [x] Workspace lifecycle actions and a providers endpoint
- [ ] A stable versioning and deprecation policy

## 7. Hermes integration

A conversational client — the voice assistant Hermes — drives the control plane
through the same public API.

- [ ] Natural-language task submission (`POST /projects/{id}/tasks` with a
      `prompt`)
- [ ] Status queries (`GET /agents/{id}/summary` is the primitive)
- [ ] Approval requests pushed out (`agent.permission_required` over WebSocket or
      webhook, answered with `POST /agents/{id}/permissions`)
- [ ] A Hermes-facing flow rebuilt entirely on the public API

The primitives exist today. The integration does not.

## 8. The payoff

The reason to have a control plane rather than a terminal.

- [ ] Task queues with priorities and a scheduling policy
- [ ] Automatic reviewers: a second agent reviews the first agent's branch
- [ ] Pull request creation
- [ ] CI integration
- [ ] Scheduled agents (nightly maintenance, dependency updates)
- [ ] Agent-to-agent delegation
